# v3.2.3 empty-target overwrite/add behavior

The two overwrite helpers now treat `DEST_VMID disk-N` as the desired final backing-volume identity even when there is no current disk to replace.

Example:

```sh
./create-disk-snapshot-and-overwrite-disk-on-vm.sh 102 disk-24 107 disk-1
```

If VM 107 has no active disk backed by `vm-107-disk-1`, the helper now:

1. verifies VM 107 and its requested state policy;
2. verifies that the physical final LV name is actually free;
3. creates the replacement under a temporary collision-free name;
4. renames it to exactly `vm-107-disk-1`;
5. verifies the Proxmox storage mapping by LV UUID;
6. attaches it to VM 107's first free `scsiN` slot;
7. verifies the final disk number and copy/snapshot identity.

No `disk-901+` archive is created because there is no displaced disk.

If `delete` is present, it is explicitly reported as a no-op in this case.

## Existing-target behavior

If `vm-DESTVMID-disk-N` is already attached as an active destination disk, the existing v3.2.2 transaction remains in effect:

```text
old disk-N -> disk-901+     preserve by default
new staged LV -> disk-N     attach at original slot/options
delete                       remove archived old LV only after success
```

## Collision rule

"Nothing to overwrite" does not mean "overwrite an orphan."

If the final LV name already physically exists but is not the active destination disk selected by the VM configuration, the helper refuses. It will not implicitly rename, delete, or overwrite an orphaned/same-name LV.

## Destination full-path form

A destination full LV path still identifies an existing disk to replace. For creating into an empty target, use the unambiguous VM/disk-number form:

```sh
DEST_VMID disk-N
```

## Validation

The disposable real-Proxmox integration group now contains separate copy and snapshot cases where the destination VM starts with no disk using the requested number. Each case verifies:

- exact final `vm-DESTVMID-disk-N`;
- first free SCSI attachment;
- no `unusedN` archive;
- no `disk-901` archive;
- `delete` does not remove the newly created result;
- copied bytes or snapshot origin are correct.
