## Remaining helper defect: inactive template/base source

The only registered helper failure was:

```text
create-disk-copy-and-add-to-vm.sh base/template naming
```

Preflight succeeded:

```text
Source LV:   /dev/plvtA.../base-...-disk-0
Source size: 33554432 bytes
```

Destination creation also succeeded.

The real block copy then failed:

```text
dd: failed to open '/dev/plvtA.../base-...-disk-0': No such file or directory
```

The source LV existed in LVM metadata and the linked-snapshot helper could snapshot it successfully. The missing element was an active block-device node.

This is normal for an inactive template/base LV: metadata existence, LVM activation, and `/dev/VG/LV` availability are separate states.

### v3.4.7 correction

The independent-copy paths now:

1. resolve source identity/size from LVM metadata;
2. check whether `$SOURCE_PATH` is already a block device;
3. if inactive, run `lvchange -ay VG/LV`;
4. record `SOURCE_ACTIVATED_BY_US=1`;
5. copy and verify;
6. run `lvchange -an VG/LV`;
7. clear the activation ownership flag.

Cleanup also attempts the deactivation after any intermediate failure.

An already-active source is never deactivated.

The activation command does not use `-p` / `--permission`, so a read-only template/base LV keeps its existing permission metadata.

The same underlying assumption existed in more than the failing helper, so the correction is applied to:

```text
copy-lvm.sh
move-lvm.sh                         (embedded corrected copy-lvm)
create-disk-copy-and-add-to-vm.sh
create-disk-copy-and-overwrite-disk-on-vm.sh
copy-disk-between-vms.sh            (embedded corrected create-copy)
clone-single-vm-disk.sh             (embedded corrected create-copy)
```

## Network group: fixture setup boundary

The network result directory contains protected baseline/after snapshots but no registered case logs. The group therefore aborted inside fixture setup before the first `run_case`.

The current fixture had already been hardened with a test-owned LXC rootfs, but setup still called:

```text
qm set ... --net0 ...
pct set ... --net0 ...
```

to create its initial NIC state.

That is the same mutation API the project helper is supposed to test. If it fails during setup, the helper never runs and there is no per-case log.

### v3.4.7 correction

Network fixture setup now:

```text
creates stopped disposable QEMU/LXC configs
creates a test-owned LXC rootfs
writes initial net0 lines directly to those stopped disposable configs
validates with qm config / pct config
```

The registered test case then becomes the **first** caller of the real `qm set` / `pct set` network mutation API through `bulk-change-vm-network.sh`.

This separates "can the fixture be constructed?" from "does the helper's Proxmox network mutation work?" and ensures any remaining platform failure is a normal logged test result.

The bridge selector also prefers a normal `vmbrN` bridge when one exists, falling back to another Linux bridge only if necessary.
