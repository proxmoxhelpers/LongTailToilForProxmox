# v3.4.0 — Disk numbering and filesystem inspection

Version 3.4.0 adds two read-only standalone helpers.

## `verify-vm-disk-numbering.sh`

This command groups LVM volumes under the Proxmox guest that references them and checks two naming invariants for managed volumes:

```text
vm-VMID-disk-N
base-VMID-disk-N
```

It highlights:

- **red** — the embedded VMID in the LV name differs from the guest that references it;
- **yellow** — the guest's active managed disk numbers do not start at `disk-0`;
- **green** — the managed numbering is consistent;
- **cyan** — informational/unmanaged LVM references.

`unusedN` entries are still displayed but are excluded from the start-at-zero decision, so intentionally archived `disk-901+` volumes do not create false warnings.

Example:

```text
VM 199 (QEMU) Copy-of-VM-win  [VMID MISMATCH]
  SLOT       LVM_PATH                                 FAMILY  LV_VMID   DISK     STATUS
  efidisk0   /dev/thinvg/base-100-disk-0             base    100       0        VMID != 199
  virtio0    /dev/thinvg/base-100-disk-1             base    100       1        VMID != 199
```

A VM whose first active managed backing number is 5 is marked:

```text
[ACTIVE STARTS AT disk-5]
```

All unreferenced LVs are shown afterward, with managed-but-unreferenced names highlighted.

## `list-all-vm-lvm-filesystems.sh`

This command performs a read-only inventory of every guest-referenced LV and then all remaining LVs.

It does **not** use `kpartx`, create device-mapper partition mappings, mount filesystems, run `fsck`, or write to the devices.

Partition discovery uses:

```text
sfdisk -d
```

Actual content detection uses low-level `blkid` probing against the exact partition byte range:

```text
blkid -p -O <byte-offset> -S <partition-size> ...
```

The output intentionally separates:

```text
TABLE_HINT
CONTENT_FORMAT
```

because a partition table normally stores a **partition type**, not an exact filesystem format.

Typical table hints include:

```text
FAT
NTFS/exFAT
MS-DATA
LINUX-FS
SWAP
LVM
RAID
BIOS-BOOT
WIN-RECOVERY
HFS+
APFS
```

Typical directly detected content includes:

```text
vfat
ntfs
exfat
ext2
ext3
ext4
btrfs
xfs
swap
LVM2_member
crypto_LUKS
linux_raid_member
zfs_member
```

When a partition type gives a definite expectation and the direct content probe contradicts it, the row receives a red note such as:

```text
MISMATCH: table=FAT content=ntfs
```

Broad types such as unknown partition GUIDs are not treated as mismatches merely because the table cannot specify an exact filesystem.

### Color families

When stdout is a terminal and `NO_COLOR` is not set:

- FAT/vfat/exFAT — green
- NTFS/MS-data — cyan
- ext2/ext3/ext4/Linux filesystem — yellow
- Btrfs/LUKS/APFS/HFS+ — magenta
- XFS/LVM/ZFS — blue
- other recognized/unknown content — white
- mismatch note — red

For an LV with no recognized partition table, the entire LV is probed as one `whole` device.

## Privilege model

`verify-vm-disk-numbering.sh` is metadata-only and does not require root where the host allows metadata access.

`list-all-vm-lvm-filesystems.sh` needs raw read access to guest block devices, so it self-elevates through `sudo` when necessary.

## Validation

The v3.4.0 inspection integration fixture includes:

1. a VM deliberately referencing `vm-OTHERID-disk-5`, which must produce both VMID-mismatch and non-zero-start warnings;
2. a disposable 64 MiB thin LV with a GPT Linux-filesystem partition and a real ext4 image written at the partition offset.

The filesystem helper must report:

```text
Partition table: gpt
TABLE_HINT        CONTENT_FORMAT
LINUX-FS          ext4
```

without creating mapper devices or mounts.
