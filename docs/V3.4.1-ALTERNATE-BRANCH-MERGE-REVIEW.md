# v3.4.1 — Alternate-branch merge review

Date: 2026-08-17

An alternate development archive was reviewed against the v3.4.0 tree file-by-file and semantically. The alternate branch identified itself as project 3.2.0 and contained some useful work that had developed differently from the later 3.4.x branch.

The merge was deliberately selective. The older branch was **not** copied over the current tree.

## Improvements accepted

### Disk-number verification

The alternate verifier detected more than a non-zero starting disk number: it also found gaps and duplicate `disk-N` values.

That logic is now in `verify-vm-disk-numbering.sh`, with one correction: only active managed disks participate in sequence analysis. `unusedN` archive entries are still displayed, but a preserved `disk-901` does not create a false numbering defect.

Examples of defects now reported:

```text
ACTIVE STARTS AT disk-5
GAP AT disk-6
DUPLICATE disk-5
```

Embedded-VMID mismatches remain a separate red condition.

### Partition/filesystem inspection

The alternate filesystem inspector used `partx --show` to obtain partition numbers, offsets, sizes and GPT/MBR types. This is cleaner than parsing `sfdisk -d` text for the same information and remains read-only.

The current `list-all-vm-lvm-filesystems.sh` therefore now uses:

```text
partx --show --raw --noheadings -o NR,START,SECTORS,TYPE
blkid -p -O <offset> -S <size>
```

The alternate branch also had a richer partition-intent table. The merged helper recognizes additional Microsoft, Linux root/home/srv, RAID, LVM, EFI, Apple and ZFS-related partition types and compares those broad table intentions with the actual on-disk content signature.

The later current-branch behavior was retained where it was better: the helper still inventories **remaining/unreferenced LVs**, not just guest-referenced disks.

### Namespace-preserving disk renumbering

The alternate branch exposed a regression in the v3.4.0 implementation. A guest can reference a stale managed namespace such as:

```text
vm-199-disk-3
vm-199-disk-7
base-100-disk-4
base-100-disk-9
```

`renumber-vm-disks.sh` must not silently skip the `base-100-*` namespace just because the guest itself is VMID 199.

v3.4.1 now renumbers each **prefix + embedded-VMID namespace** independently:

```text
vm-199-disk-3  -> vm-199-disk-0
vm-199-disk-7  -> vm-199-disk-1

base-100-disk-4 -> base-100-disk-0
base-100-disk-9 -> base-100-disk-1
```

The alternate branch also had a shared-volume ownership guard that the current branch had lost. That guard is restored: renumbering refuses a configured LV that is also referenced by another guest.

### Safer volume-name repair

The alternate branch correctly included these QEMU references when looking for backing volumes to repair:

```text
efidiskN
tpmstateN
```

They are restored alongside normal disk and `unusedN` entries.

For an already-managed stale name, v3.4.1 also adopts the safer exact-correction rule:

```text
base-100-disk-1 -> base-199-disk-1
```

If `base-199-disk-1` already exists, the helper now refuses the operation. It does **not** silently change the corrected disk number merely to find a free name.

Planned-name collision checks are keyed by both volume group and LV name, avoiding false cross-VG collisions while still rejecting a real same-VG collision.

### Foreign managed-name warning during VMID changes

`change-vmid-of-vm.sh` still renames only managed names that actually embed the source VMID. If the configuration also contains a stale/foreign managed name, v3.4.1 now calls that out before mutation instead of silently omitting it from the rename plan.

Example:

```text
VM 199 references base-100-disk-1
```

A VMID change of 199 will warn that this name is foreign to VMID 199 and leave it unchanged. `fix-vm-volume-names.sh` remains the explicit repair operation.

### Strict managed disk-number ambiguity

The later branch could prefer an exact current-VMID backing name over a second configured stale `vm-/base-` backing name with the same `disk-N`. That makes a numeric selector look unambiguous when the guest configuration is actually ambiguous.

v3.4.1 changes numeric selectors in:

```text
move-disk-to-vm.sh
create-disk-copy-and-add-to-vm.sh
create-disk-snapshot-and-add-to-vm.sh
create-disk-copy-and-overwrite-disk-on-vm.sh
create-disk-snapshot-and-overwrite-disk-on-vm.sh
```

If more than one configured managed volume has the requested `disk-N`, the command refuses and asks for an explicit source or destination slot.

## Alternate changes deliberately not imported

### The alternate tree itself

The alternate archive identifies itself as project 3.2.0. Replacing the current tree with it would regress later work, including:

- overwrite transactions that preserve the destination backing disk number;
- `disk-901+` archive behavior and `delete`;
- UUID-safe overwrite verification and rollback;
- empty-target overwrite/create behavior;
- exact source/destination QEMU slot selectors;
- bare destination bus selectors;
- `hot|pause|stop|restart`;
- the `boot` keyword;
- the current standalone wrapper payloads and expanded integration suite.

Those current behaviors remain intact.

### Alternate inspection-helper names

The alternate branch used:

```text
verify-disk-numbering.sh
list-all-vm-disk-formats.sh
```

The current public names remain:

```text
verify-vm-disk-numbering.sh
list-all-vm-lvm-filesystems.sh
```

This avoids unnecessary command-name churn.

### Always creating `vm-DEST-disk-N`

The older alternate base-volume work suggested always creating a `vm-DEST-disk-N` destination even for a template. The later current branch explicitly distinguishes normal VM and template destinations and can use:

```text
base-DEST-disk-N
```

for a template.

That later behavior was retained. Changing it during this merge would be a semantic regression without real-system evidence that the older rule is preferable.

## Validation boundary

The accepted changes pass the local POSIX/static/standalone tests, but several are Proxmox/LVM transaction semantics and therefore still require the disposable real-host integration suite.

Focused groups:

```sh
./tests/groups/10-inspection.sh --run --verbose
./tests/groups/40-disk-lifecycle.sh --run --verbose
./tests/groups/50-copy-snapshot.sh --run --verbose
./tests/groups/60-disk-config.sh --run --verbose
./tests/groups/80-vm-config.sh --run --verbose
```

Then:

```sh
./tests/run-all-tests.sh --run --verbose
```

Do not promote v3.4.1 to the integration-validated baseline until the full run returns zero failures and zero anomalies.
