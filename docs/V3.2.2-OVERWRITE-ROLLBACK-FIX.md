# v3.2.2 overwrite rollback / identity fix

A real Proxmox run of `create-disk-snapshot-and-overwrite-disk-on-vm.sh` exposed two independent defects in v3.2.1.

## 1. False storage-mapping failure after LV rename

The staged replacement was created under a temporary backing name, for example:

```text
vm-108-disk-1
```

and was then renamed to the destination disk number:

```text
vm-108-disk-0
```

v3.2.1 updated the logical volume name variables but retained a pre-rename path variable. The subsequent `pvesm path` verification compared the correct final Proxmox path against that stale staged path and could falsely report:

```text
ERROR: Proxmox storage mapping does not point to the new LV.
```

v3.2.2 records the replacement LV UUID immediately after creation. Every later mapping verification resolves the current Proxmox volume ID and verifies that the resolved LVM LV has the same UUID. LV renames therefore cannot invalidate identity verification.

## 2. Unsafe rollback of an unused disk

v3.2.1 rollback removed the temporary `unusedN` entry with:

```text
qm set VMID --delete unusedN
```

before restoring the archived LV name.

On Proxmox, removing an `unusedN` device through the VM configuration path may also free the backing storage volume. That means a rollback could destroy the very archived LV it was attempting to restore.

v3.2.2 never uses `qm --delete unusedN` during rollback.

Instead it:

1. identifies the original destination LV by its saved LV UUID;
2. moves the replacement out of the original disk number when necessary;
3. renames the original LV back to its original `vm-VMID-disk-N` name;
4. keeps the temporary unused reference storage-neutral while the original disk is reattached;
5. removes only the stale config line after the original disk is attached;
6. verifies the original destination slot again references the original volume.

Config-only `unusedN` rewrites/removals are performed without invoking Proxmox's unused-volume deletion path.

## Rollback preservation rule

If rollback cannot locate the original LV UUID or cannot safely restore the original slot, automatic cleanup stops.

The replacement LV is intentionally left intact instead of being automatically removed. This maximizes the amount of recoverable storage state available for manual repair.

## `delete` mode

`delete` remains intentionally delayed until after the replacement is attached, verified, and requested VM-state restoration succeeds.

The archived unused config reference is removed without `qm --delete`, then the exact archived LV is explicitly removed. If explicit LV deletion fails, the script attempts to restore the unused config reference.

## Acceptance

Static validation proves the new UUID/rollback invariants are present, but the complete transaction still requires real Proxmox validation:

```sh
./tests/groups/50-copy-snapshot.sh --run --verbose
```

then:

```sh
./tests/run-all-tests.sh --run --verbose
```
