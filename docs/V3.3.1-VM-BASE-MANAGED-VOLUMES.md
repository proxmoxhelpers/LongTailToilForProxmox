# v3.3.1 — Managed `vm-` and `base-` LVM volumes

Proxmox LVM/LVM-thin managed disks can appear in two naming families:

```text
vm-VMID-disk-N
base-VMID-disk-N
```

`vm-` is the normal writable VM-volume family. `base-` is used by template/base volumes and can also appear as an origin for linked thin volumes.

## Project rule

Whenever a helper is *discovering or interpreting an existing managed volume*, both families are valid. The helper must not silently ignore `base-*` merely because older code expected `vm-*`.

When a helper *renames* an existing managed volume, it preserves its family:

```text
vm-100-disk-1   -> vm-200-disk-1
base-100-disk-1 -> base-200-disk-1
```

When a helper *creates* a new destination volume:

- a normal VM destination uses `vm-DESTVMID-disk-N`;
- a template destination uses `base-DESTVMID-disk-N`;
- an overwrite of an existing managed target preserves that target's current family.

## Stale embedded VMIDs

A guest configuration can legitimately be encountered in an inconsistent historical state, for example VMID 199 referencing:

```text
base-100-disk-0
base-100-disk-1
```

A numeric selector such as `199 disk-1` first searches for an exact current-ID managed name:

```text
vm-199-disk-1
base-199-disk-1
```

If no exact match exists, it may fall back to a configured `vm-*` or `base-*` volume with the requested disk number and a stale embedded VMID **only when exactly one match exists**. Ambiguity is an error.

`fix-vm-volume-names.sh` then preserves the family while normalizing the embedded VMID, for example:

```text
base-100-disk-1 -> base-199-disk-1
```

provided the destination name is free.

## Helpers changed in v3.3.1

Material naming changes were made to:

- `change-vmid-of-vm.sh`
- `renumber-vm-disks.sh`
- `fix-vm-volume-names.sh`
- `find-orphaned-volumes.sh`
- `recover-vm-from-volumes.sh`
- `move-disk-to-vm.sh`
- `create-disk-copy-and-add-to-vm.sh`
- `create-disk-snapshot-and-add-to-vm.sh`
- `create-disk-copy-and-overwrite-disk-on-vm.sh`
- `create-disk-snapshot-and-overwrite-disk-on-vm.sh`
- embedded standalone payloads in `copy-disk-between-vms.sh`, `snapshot-disk-between-vms.sh`, and `clone-single-vm-disk.sh`

The rest of the project was audited. Helpers that resolve storage by configured slot, storage ID, canonical path or LV UUID rather than by a `vm-*` name regex were left generic rather than receiving unnecessary naming logic.

## Validation boundary

Static and plan-only tests can prove parsing, naming contracts and transaction construction, but template/base behavior also depends on real Proxmox/LVM semantics. v3.3.1 should not be promoted to the integration-validated baseline until the new template fixtures have passed on a disposable Proxmox test host.
