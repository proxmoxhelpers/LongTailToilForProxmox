# v3.5.0 — Project-wide Shell Style Refactor

Date: 2026-08-17

v3.5.0 applies the updated POSIX shell style conventions to all 42 public helpers.

## Lifecycle placement

Every public helper now begins, after the shebang, `set -eu`, and documentation banner, with:

```text
setup()
main()
end()
usage()
```

Implementation/runtime helpers follow afterward.

`usage()` is deliberately adjacent to `end()`.

## Setup defaults

Script/default state is initialized at the top of `setup()` before setup helper calls such as `define_colours`, argument parsing or elevation detection.

This makes the operator-visible defaults and command state easy to locate.

## Elevation output

Elevation detection is silent when already root.

Removed:

```text
[OK] Elevation: running as root.
```

The scripts report elevation only when the requested operation requires root and the current process is not elevated.

## Function call documentation

Functions that consume positional arguments now have explicit call syntax in their nearby documentation, using either:

```text
# Call: function ARG1 [ARG2]
```

or a full `Usage:` documentation field.

## Function variable prefixes

Function scratch variables use one function-derived prefix consistently.

Examples:

```text
require_qemu_vm()             -> rqv_
set_destination_boot_first() -> sdbf_
collect_guest_lvm_references() -> cglr_
```

Legacy inconsistencies such as `bf_` inside `build_fix_plan`, `ar_` inside `apply_renumber_plan`, and `rb_` inside `rollback_old_disk` were normalized.

Script-wide caller-visible state remains uppercase.

## Function-persistent state

A private variable deliberately intended to retain function-specific state after return, until the next invocation of that function, uses a leading underscore before its function prefix:

```text
_fn_cached_value
_RQV_CachedValue
```

Ordinary POSIX scratch-variable leakage does not make a variable "persistent" for this rule; callers must not consume scratch state after return.

## Pseudoarrays and pseudoobjects

The style guide accepts conceptual notation:

```text
fn_myarray[X]
fn_myarray.lbound
fn_myarray.ubound
fn_myarray.count
fn_myobject.property
```

with an implicit array lower bound of 0 unless documented otherwise.

Literal `[` `]` and `.` are not valid POSIX shell variable-name characters, so the notation is conceptual. Executable POSIX helpers continue to prefer:

```text
newline-delimited plan/state files
pipe-delimited records
function-prefixed scalar variables
subshell output
```

rather than dynamic pseudoarray variable names.

## Validation boundary

This refactor is intended to preserve behavior, but it touches every public shell file and regenerated embedded companion payloads. Therefore v3.5.0 requires a fresh real-Proxmox integration run before it can inherit an integration-validated status.
