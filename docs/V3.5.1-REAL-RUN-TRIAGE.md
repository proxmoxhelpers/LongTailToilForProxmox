## Failure 1 — copy-add from inactive base/template source

`create-disk-copy-and-add-to-vm.sh` failed on the real operation after its dry-run passed:

```text
Source LV is inactive; temporarily activating it for the block copy...
ERROR: Source LV activation succeeded but no block device appeared:
       /dev/<test-vg>/base-<vmid>-disk-0
```

The source fixture was created by converting a disposable QEMU VM to a Proxmox template and then explicitly deactivating its `base-*` LV.

## Failure 2 — copy-overwrite from inactive base/template source

`create-disk-copy-and-overwrite-disk-on-vm.sh` failed at the same source-activation point.

The failure happened before replacement LV creation or destination detach/rename/attach mutation.

## Root cause

Proxmox template `base-*` LVs may be marked with LVM's activation-skip property.

For such an LV:

```sh
lvchange -ay VG/base-VMID-disk-N
```

may return success while LVM intentionally skips activation. Therefore checking only the command exit status is insufficient.

The correct temporary activation is:

```sh
lvchange -ay -K VG/base-VMID-disk-N
```

where `-K` means ignore activation-skip.

The helpers still verify that the block device actually exists after activation. They do not alter LV permission metadata and they restore a source activated by the helper to its original inactive state.

The test byte comparator had the same issue and also requires `-K`.

## Network anomaly

All three `bulk-change-vm-network.sh` cases passed, including the missing-guest refusal/no-mutation case.

Cleanup then reported:

```text
Refusing to destroy CT <id> because one or more storage references are not provably test-owned.
One or more disposable guest configs remain; refusing storage/VG cleanup...
Protected-state difference detected in guests...
```

The protected-state diff contains the single retained disposable LXC config and no guest-runtime, firewall, storage, VG, PV, or LV protected-state difference.

The v3.4.7 `90-network.sh` fixture created an LXC rootfs using `$TEST_VG_A/$TEST_STORAGE_A` but did not call `create_storage_sandbox` first. This violates the harness ownership model.

v3.5.1 fixes the test definition by:

1. checking for an existing bridge first;
2. calling `create_storage_sandbox`;
3. proving `TEST_STORAGE_A` is owned by the current run;
4. only then creating the CT rootfs fixture.

This is a test-harness correction, not a `bulk-change-vm-network.sh` product behavior change.
