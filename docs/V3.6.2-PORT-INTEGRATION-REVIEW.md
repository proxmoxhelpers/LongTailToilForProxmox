# v3.6.2 Selective Port and Integration Review

## Scope

Project **v3.6.2** selectively ports the **40 commands that were new in the alternate v3.6.1 draft** onto the newer v3.5.2 baseline. The alternate copies of the original 42 helpers were not used as replacements, because that would have reintroduced behavior already corrected in v3.5.2.

The result contains **82 public standalone commands**.

## Code/documentation contract

For all 40 newly ported commands:

- the script parses with POSIX `/bin/sh`;
- the first public lifecycle functions are `setup()`, `main()`, `end()`, `usage()`;
- every argument-consuming function has an immediately attached `Call:`/`Usage:` contract;
- every new command-specific public function has a descriptive comment block;
- `--help` and `--version` return successfully without crossing the mutation boundary;
- every parser option is represented in built-in `--help`;
- live `--help` is byte-for-byte identical to `docs/<command>.usage`;
- the Markdown page embeds that exact live help;
- the Markdown Purpose is derived from and normalized to the script's DESCRIPTION;
- each command has a real integration-group reference;
- every command classified as mutating has a `run_dryrun_unchanged` integration case.

The original 42 commands retain the v3.5.2 help/documentation and safety contracts, with their behavior retained and their script/project release identity normalized to v3.6.2.

## Safety changes applied during the port

### Physical identity instead of storage-ID spelling

Safety decisions in the new runtime resolve LVM references to LV UUIDs. Two different Proxmox storage aliases that expose the same LV are therefore treated as one physical volume. Shared/reference checks do not rely on the literal `storage:volume` string.

### Inactive and activation-skip LVs

Inspection/copy helpers that need a block node can temporarily activate inactive LVs with `lvchange -ay -K` in real mode and restore the original inactive state on every exit path. Dry-run/preflight never activates the LV and refuses operations that cannot be truthfully completed without activation.

### Independent-copy cleanup

The four new copy/conversion primitives capture the destination LV UUID immediately after creation. Failure cleanup may remove the incomplete destination only while that exact UUID still owns the destination name. Source activation restoration happens before failure cleanup that might itself fail.

### Direct VM-config editing

Reference-only, slot-renumber/sort and repair helpers use strict slot validation, stopped-guest checks where required, snapshot-section refusal for non-section-aware rewrites, config backup, exact postcondition verification and abnormal-exit rollback.

### Mount ownership

`mount-vm-filesystems.sh` records the exact mounts, mapper devices, temporary activations and directories created by one invocation. It refuses pre-existing mapper ambiguity and verifies the canonical mounted source. `unmount-vm-filesystems.sh` consumes that ownership record, validates all recorded source/target identities before the first unmount and cleans only recorded resources.

### Growth boundaries

Block growth and filesystem growth are separate operations. `resize-vm-disk.sh` and `extend-lvm.sh` are grow-only and verify byte-size postconditions. `grow-vm-filesystem.sh` never grows the block device; mounted XFS requires an exact mountpoint whose canonical source matches the selected device, while supported ext-family whole-device growth remains offline.

### Flatten/clone/migration transactions

`flatten-vm-disk.sh` tracks old/new LV UUIDs and restores the original active slot on abnormal exit. `clone-vm-storage-only.sh` restores the destination config and cleans only provably invocation-owned imported storage after failure; stopped-source copies receive full byte comparison, while `--hot` explicitly does not claim stable post-copy byte equality. `migrate-vm-storage-layout.sh` maintains a completed-move plan and attempts reverse-order rollback after interrupted/failed transactions.

### Journals, archives and remote restore

Operation journals use a root-owned, non-symlink journal root and unpredictable root-only `mktemp` files. Whole-VM archives validate member names/types/duplicates and checksum coverage before restore code is trusted. Checksums are documented as integrity, not authenticity. The remote workflow reserves an absent remote output path and verifies the SHA-256 of the complete transferred archive before executing its embedded restore.

### Bulk execution

`for-each-vm.sh` constructs argv explicitly and never uses `eval`; newline-bearing arguments are refused, filters are validated before dispatch and the literal `{}` placeholder is substituted exactly per argument.

## Validation result

The current static/CLI suite passes:

```text
Passed    : 71
Failed    : 0
Skipped   : 0
Anomalies : 0
```

The static group includes the original v3.5.2 contracts, the alternate branch's useful help/source/archive/growth checks, and six v3.6.2-specific hardening contracts for synchronized physical-identity runtime behavior, failure cleanup, mount ownership, direct-config transactions, exact filesystem growth and journal/remote-transfer safety.

The integrated real test definition contains **137 cases across 14 operational groups**. Those cases require a disposable real Proxmox/LVM environment and were not executed during this port. Project v3.5.1 therefore remains the last completed real-Proxmox acceptance baseline; v3.6.2 is **statically validated / release candidate** until its own real-host run is clean.
