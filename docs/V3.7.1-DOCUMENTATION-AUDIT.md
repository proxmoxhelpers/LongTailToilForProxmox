# v3.7.1 Documentation / Usage / Code Audit

## Status

Project **v3.7.1** was re-audited documentation-first and code-first on
**2026-08-22** after the successful real-Proxmox acceptance run. A repository
identity follow-up was completed on **2026-08-26**.

The follow-up standardizes the project name as **LongTailToilForProxmox** and
the canonical repository as
<https://github.com/proxmoxhelpers/LongTailToilForProxmox>. It changes
documentation/repository references plus the matching static URL expectation
only. No production helper, shared shell library, or operational integration
group behavior is changed.

## Scope

The audit covers the complete current public surface:

- **81** top-level public `.sh` commands;
- **81** per-helper Markdown pages in `docs/`;
- **81** `.sh.usage` snapshots in `docs/`;
- the 81-command inventories in `README.md`, `docs/HELPERS.md`, and
  `tests/TEST-MATRIX.md`;
- current project/test overview documents and reusable testing guides;
- local Markdown links throughout the repository;
- version-stamped release/history documents for stale-current wording that
  could be mistaken for the present release.

Version-stamped `docs/V3.x...` files remain historical records. Their historical
counts and release conclusions are not rewritten as if they described v3.7.1.
Where a generic/current-facing document used old release wording as though it
were still current, that wording was corrected.

## Repository identity follow-up

All full project-name references and repository paths were normalized to
**LongTailToilForProxmox**. This includes README titles and prose, per-helper
raw-download URLs, clone/install instructions, publishing guidance, historical
artifact references, and the static contract that checks generated download
commands.

Compatibility-oriented internal identifiers such as
`LONGTAILTOIL_JOURNAL_DIR`, `.longtailtoil-*` ownership-state filenames, and
embedded heredoc labels remain unchanged because they are runtime/internal
interfaces rather than project-name branding. Renaming them would create
needless compatibility risk.

## Live help and usage result

Each public command was executed locally with `--help` and `--version`.

For every one of the **81/81** commands:

1. `--help` exits successfully;
2. live help is byte-for-byte identical to `docs/<command>.sh.usage`;
3. the `<!-- BEGIN LIVE HELP -->` block in `docs/<command>.md` is
   byte-for-byte identical to the same live output;
4. `--version` exits successfully and identifies project v3.7.1;
5. the per-helper page identifies the helper as shipped in project v3.7.1.

No `.usage` snapshot required regeneration because all 81 already matched the
actual implementation exactly.

## Parser, call-syntax, and documentation contracts

The project static suite independently enforces the interface-level properties
that are difficult to validate by prose review alone:

- every parsed option is present in live help;
- incomplete required arguments print usage;
- all documented help aliases work;
- argument-taking functions document their call syntax;
- common-option/version ordering is accepted;
- live help, `.usage`, and helper-page help blocks remain synchronized;
- every public command has documentation and an integration reference.

These contracts remained green after the documentation corrections.
